# Booking failure modes and exact fallback behaviour

Every path below is implemented in `app/booking/service.py` and covered by `tests/test_booking.py`
(mocked Zoom) or `tests/test_guardrails.py` (no model call). Nothing in this table is aspirational.

| # | Case | Detection | What the visitor sees | What happens server-side |
|---|------|-----------|-----------------------|--------------------------|
| 1 | **No slots available** in the window | Availability call succeeds, zero `status=available` spots after dropping anything < 30 min away | "No open slots in that window." + button **Open the booking page** (plain Zoom link). The model can widen the window (`days_ahead` up to 30) and retry once. | `get_available_slots` returns `ok=false, error=no_slots`. No lead is created unless the visitor leaves details, in which case `book_slot` with an unavailable time is not called; instead the model offers the link and email. |
| 2 | **Scheduler timed out / API changed** | `httpx` timeout (8 s), non-200, non-JSON, or JSON without `days[].spots[].startTime` | "Zoom's scheduler isn't responding right now." + plain booking link. If it happens at **confirm** time (after name/email/reason were collected): "I've sent Deep your details and the time you wanted; you can also book directly here: <prefilled link>". | Official client fails → public fallback tried → both fail → `AvailabilityError`. At confirm time the lead is saved with `status=enquiry` and the host brief is emailed **before** the link is returned, so the lead survives. Logged as `error`/`lead`. |
| 3 | **Slot taken between showing and confirming** | `book_slot` re-fetches a ±1 h window and requires an exact `start` match with `status=available` | "That slot was just taken. Let me fetch fresh times for you." The model calls `get_available_slots` again and shows three new buttons. | `status=slot_taken`, no hand-off URL, no lead row (the visitor is still in the flow). If `ZOOM_ENABLE_API_BOOKING=true` and Zoom's create-booking returns a conflict, the same path is taken. |
| 4 | **Timezone mismatch** | Visitor zone comes from the browser (`Intl`), never from the model. `start` must carry an offset; naive times and unknown IANA zones are rejected before any network call. | Slots are always rendered as `Tue 06 Oct, 08:00 (America/New_York)` with the host time underneath (`17:30 (Asia/Kolkata)`). If the model passes a naive time: "I couldn't pin down that time… please pick one of the listed slots." | Same instant in a different zone is accepted (compared in UTC). Unknown zone in `get_available_slots` falls back to the host zone and the label says so. |
| 4t | **Tracking beacon fails or geo provider is down** | `/track` returns `{"ok": false}` and the chat continues; `touch()` still creates the session row on the first message; the geo lookup is retried on the next session from that IP (only successes are cached); `geo_status` shows `failed`/`pending` in `/admin` |
| 4u | **Spoofed `X-Forwarded-For`** | Only honoured when `TRUST_PROXY=true`; set it `false` when the app is not behind Cloudflare/nginx, else a caller can pick their own location and dodge rate limits |
| 5a | **Off-topic question** | Best retrieval score below `RETRIEVAL_MIN_SCORE` (0.60 on the bge-small scale, calibrated in TEST_LOG.md) and no booking intent; questions that clear the gate but aren't on the site are declined by the model under prompt rules 1 and 5 | Polite refusal with the Zoom link and email. No sources, no guess. | No model call (zero cost). Logged as `refusal` with `best_score`. |
| 5b | **Prompt-injection attempt** | Regex pre-filter on the user message; plus rule 4 of the system prompt and the fact that side effects exist only as validated tools | "I follow a fixed set of rules and can't change them from chat…" | No retrieval, no model call. Logged as `injection` with the first 300 chars. Injected text inside *page content* is fenced in `<sources>` with role tags stripped; the model is told it is data. |
| 5c | **Unknown or unloadable call type** (model passes a slug that is not one of the three, or the schedule list cannot be fetched) | `schedule_by_slug` returns none / `AvailabilityError` | The three real call types are shown as buttons to pick from; if the list itself is down, the plain booking page link. At confirm time: lead saved as `enquiry`, host brief sent, plain link returned. | `error=unknown_schedule` with `choices`, or `unavailable`. The list is cached 10 min, so a brief Zoom outage does not hide the call types. |
| 6 | **Host brief email fails** (SMTP down / not configured) | `send_host_brief` returns false | Hand-off still proceeds; the UI adds "Note: your details were saved for Deep." | Lead row exists with `brief_sent=false`; an operator can replay from the `leads` table. |
| 7 | **Daily spend cap reached** | `usage_daily.usd >= DAILY_SPEND_CAP_USD` | "The assistant has hit its daily budget. Please book directly at … or email …" | No model call. Logged as `spend_cap`. |
| 8 | **Rate limit** (20/min, 200/day per IP) | In-memory sliding window | HTTP 429, UI says "Slow down a little". | Logged as `rate_limited`. |

## What the bot never does
* Invent a time. Every slot shown came from a live availability response seconds earlier.
* Confirm a booking it did not verify. Without `ZOOM_ENABLE_API_BOOKING` it hands off to Zoom; the word "booked" only appears after Zoom's create-booking call returns 2xx.
* Send email or create bookings from free text. Both are tools with validated arguments.
